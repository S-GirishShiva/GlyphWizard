# M0 learning asides

Short explanations of each new Android/Kotlin concept as M0 introduces it (D23), with a Go/Python analogy where one fits.

## Gradle modules
A Gradle build is a tree of **modules** (Gradle calls them projects). Each has its own `build.gradle.kts`, dependencies and outputs, and they're listed in `settings.gradle.kts`. That's like several Go packages in one repo sharing a `go.work`. Ours split by responsibility: `:core` and `:agent` are plain Kotlin (no Android) so they test fast and run anywhere, `:glyph-sdk` isolates the Nothing SDK, `:designsystem` holds UI tokens, and `:app` wires everything.
- [Gradle: multi-project builds](https://docs.gradle.org/current/userguide/multi_project_builds.html) · [Android: modularization](https://developer.android.com/topic/modularization)

## The version catalog
`gradle/libs.versions.toml` is the single list of dependency and plugin versions. Modules refer to aliases (`libs.compose.bom`, `alias(libs.plugins.detekt)`) instead of repeating coordinates, a bit like a shared `go.mod` `require` block that every package reads. Each pin carries its upload date and source, because of our "stable and ≥ 14 days old" rule.
- [Gradle version catalogs](https://docs.gradle.org/current/userguide/version_catalogs.html) · [Android: migrate to version catalogs](https://developer.android.com/build/migrate-to-catalogs)

## Product flavours
A **flavour** is a variant of the same app built from extra source folders. That's like Go build tags choosing which files compile. `sdkFree` builds with `src/sdkFree/` and never touches the Nothing SDK; `full` builds with `src/full/` and links the SDK. Combined with build types (`debug`/`release`) they produce variants such as `sdkFreeDebug`, and tasks are named after them (`assembleSdkFreeDebug`).
- [Configure build variants](https://developer.android.com/build/build-variants)

## `Application` vs `Activity`
The `Application` object is created once when the app's process starts, before anything else: it's the process entry point, like `main()`. An `Activity` is one screen with a lifecycle (created, started, stopped, destroyed) that Android drives as the user navigates. We keep one `ComponentActivity` that hosts Compose, and put long-lived wiring on the `Application`.
- [Application fundamentals](https://developer.android.com/guide/components/fundamentals) · [The activity lifecycle](https://developer.android.com/guide/components/activities/activity-lifecycle)

## The manual DI container
`AppContainer` builds every long-lived object and hands dependencies to constructors. That's exactly the wiring you'd write in Go's `main.go`. There's no Hilt/Dagger (annotation-processing frameworks) and no service locator: you can read the whole graph in one file. `GlyphWizardApplication` creates it lazily with `by lazy`, which Kotlin makes thread-safe.
- [Manual dependency injection](https://developer.android.com/training/dependency-injection/manual)

## Kover, ktlint and detekt
- **ktlint** formats and checks style, like `gofmt` plus style lints.
- **detekt** finds code smells and our banned patterns, like `go vet` plus `golangci-lint`.
- **Kover** measures test coverage, like `go test -cover`, and fails the build below our thresholds.

Some detekt rules need **type resolution**: they ask the compiler what a call *resolves to* (is this `runBlocking` the coroutines one?), which only the type-resolved tasks (`detektMain`, `detektSdkFreeDebug`) can do. The plain `detekt` task works on syntax alone, like `grep` vs `go vet`. A canary module with deliberate violations proves detekt still reports them.
- [detekt type resolution](https://detekt.dev/docs/gettingstarted/type-resolution/) · [ktlint](https://pinterest.github.io/ktlint/) · [Kover](https://kotlin.github.io/kotlinx-kover/gradle-plugin/)

## The four "Java versions"
1. **Daemon JVM:** the JDK that *runs Gradle* and its plugins (AGP, the Kotlin compiler, detekt). Ours is 25, set in `gradle/gradle-daemon-jvm.properties`. It's like the Python interpreter running your build script.
2. **Toolchain:** the JDK that JVM modules compile against and run their tests on. Ours is 25, via `jvmToolchain(25)`. Like pointing `GOROOT` at a specific Go version.
3. **Bytecode target:** the class-file format version the compiler writes (Java 25 = major version 69). On Android, D8 rewrites class files into DEX anyway, so this number matters little there.
4. **On-device API level:** which `java.*` classes really exist on the phone, governed by `minSdk`. This is the one that crashes at runtime. `:core` and `:agent` end up inside the APK but compile as plain JVM code, so they use `-Xjdk-release=17`: calling a newer JDK API (say Java 21's `Thread.ofVirtual()`) becomes a compile error instead of a `NoSuchMethodError` on the phone.

Why it was "17" before: AGP *requires at least* JDK 17, and early research mistook that minimum for a target (D54).
- [Java versions in Android builds](https://developer.android.com/build/jdks) · [Gradle toolchains](https://docs.gradle.org/current/userguide/toolchains.html) · [Kotlin compiler options](https://kotlinlang.org/docs/compiler-reference.html)

## Robolectric and `--add-opens`
**Robolectric** runs Android code (Activities, Compose UI) on your laptop's JVM by simulating the framework, so UI tests are fast local tests, like `httptest` standing in for a real server. It peeks into JDK internals by reflection, and modern JDKs lock those down by default. So the Android modules' test JVMs get `--add-opens=java.base/jdk.internal.access=ALL-UNNAMED`: an explicit, narrow permission. SDK 36 tests need JDK ≥ 21, which is one reason those tests run on the JDK 25 daemon.
- [Robolectric: getting started](https://robolectric.org/getting-started/) · [JEP 403: strongly encapsulate JDK internals](https://openjdk.org/jeps/403)

## `createComposeRule()` and `ui-test-manifest`
A Compose UI test needs an Activity to draw into. `createComposeRule()` launches a blank `ComponentActivity`, which must be declared in a manifest, and the `ui-test-manifest` artifact ships that declaration for debug builds. `:app`'s tests instead use `createAndroidComposeRule<MainActivity>()`, which launches our real Activity and so also works in release unit tests.
- [Test your Compose layout](https://developer.android.com/develop/ui/compose/testing)

## Lint as errors
Android Lint checks Android-specific mistakes (outdated SDK checks, missing permissions, resource problems). By default only *errors* fail the build, so we set `warningsAsErrors = true` ("Lint clean" is in our definition of done). Deliberate exceptions are disabled by name with a reason, e.g. `OldTargetApi`, because target 36 is a decision (D31).
- [Improve your code with lint checks](https://developer.android.com/studio/write/lint)

## Explicit backing fields
Kotlin 2.4 lets a property expose a read-only type while storing a mutable one:
```kotlin
val items: List<Int>
    field = mutableListOf()
```
Outside the class, `items` is a `List`; inside, it's the `MutableList`. It replaces the old `_items`/`items` pair. M0's canary confirmed that the compiler, ktlint and detekt all accept it.
- [What's new in Kotlin 2.4](https://kotlinlang.org/docs/whatsnew24.html)

## Fetching the Nothing SDK through Gradle (M0 Task 3)
The SDK isn't on Maven Central, it's a file in Nothing's GitHub repo. We still let **Gradle's dependency system** download it, by declaring that repo as a tiny Ivy repository (a layout of plain file URLs) that may serve only this one module (`exclusiveContent`).
- **Why not our own download code:** the JDK's HTTP clients connect to only the *first* address DNS returns. GitHub's CDN returns 8; when one is unreachable (it happened on our network), the download fails at random. Gradle's HTTP client tries every address, the way curl and browsers do.
- **What we get for free:** caching, `--offline` mode, and **dependency verification**.
- [Resolving specific artifacts (Ivy pattern layouts)](https://docs.gradle.org/current/userguide/resolving_specific_artifacts.html) · [Filtering repositories / exclusiveContent](https://docs.gradle.org/current/userguide/filtering_repository_content.html)

## Dependency verification (`gradle/verification-metadata.xml`)
Like Go's `go.sum`: a committed list of SHA-256 checksums for every artifact the build downloads (plugins, libraries, the SDK). If a download's hash differs (compromised mirror, changed upstream), the build stops with "Dependency verification failed". Generate it from an **empty Gradle home**: Gradle caches parsed metadata, so a warm cache skips files it would read on a fresh machine (we hit exactly this: parent POMs were missing until we regenerated cleanly).
- [Gradle dependency verification](https://docs.gradle.org/current/userguide/dependency_verification.html)

## `implementation` vs `compileOnly` vs `runtimeOnly`
- `implementation`: compile against it and ship it.
- `compileOnly`: compile against it but don't ship it (like coding against a Go interface whose implementation is linked elsewhere).
- `runtimeOnly`: ship it, but don't let code compile against it.

The plan first used `compileOnly` for the SDK, because AGP refuses to bundle a *local* `.aar` file into a library. Once the SDK became a normal external module, plain `implementation` in the `full` flavour (`fullImplementation`) was right, and the apps receive it transitively.
- [Add build dependencies](https://developer.android.com/build/dependencies)

## Pinning by commit and hash
The SDK's "version" is a git commit SHA, so the URL always names the exact same bytes, and the SHA-256 in the verification file proves we got them. Two independent locks: the commit fixes *what* we ask for, and the hash checks *what we received*.

## Configuration cache, and why tests must sometimes bypass it
Gradle's configuration cache stores the result of configuring the build, including already-resolved file lists, so the next run starts instantly. It's great for speed, but a test that deletes a cached file must use `--no-configuration-cache` (and a fresh Gradle home), or Gradle replays the old answer and the test proves nothing.
- [Configuration cache](https://docs.gradle.org/current/userguide/configuration_cache.html)

## Flavour and build-type source sets (M0 Task 4)
Besides `src/main`, each variant dimension has its own source folder, compiled only into that variant:
- `src/sdkFree` and `src/full` give `GlyphDisplays` two implementations (no SDK vs Nothing SDK).
- `src/debug` and `src/release` give `wrapForBuild` two (mirror vs none).
- Tests follow the same scheme: `src/testFull` holds tests that need the full flavour's classes.

It's Go build tags again: the same function name, chosen at build time, no runtime `if`. Both versions must share one signature, which is why the release `wrapForBuild` carries a parameter it doesn't use.
- [Configure build variants: source sets](https://developer.android.com/build/build-variants#sourcesets)

## `suspendCancellableCoroutine`: callbacks into suspend calls
The Nothing SDK reports "service connected" through a callback. `suspendCancellableCoroutine` pauses `connect()` until our callback calls `continuation.resume(...)`. It's like a goroutine blocking on a channel that the callback sends into. Wrapping it in `withTimeoutOrNull(3.seconds)` bounds the wait, and `invokeOnCancellation` cleans up (unbinds) if the caller gives up. In tests, `runTest` uses *virtual time*, so the 3-second timeout test runs instantly.
- [Kotlin: suspendCancellableCoroutine](https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-core/kotlinx.coroutines/suspend-cancellable-coroutine.html) · [Testing coroutines](https://developer.android.com/kotlin/coroutines/test)

## Interfaces defined by the consumer
`MatrixService` lists only the six things `NothingGlyphDisplay` needs from the Nothing SDK, and lives next to it: Go's "accept interfaces" idiom. `SdkMatrixService` is the one small class that touches `com.nothing.*`, and every test uses a fake instead, so no test needs the real service or SDK types.

## Binder calls and threads
Android apps talk to system services (like Nothing's glyph service) through **Binder**, Android's inter-process call mechanism, similar to a local RPC. A call such as `setAppMatrixFrame` blocks until the other process answers, so it must never run on the main (UI) thread, which would freeze the screen. The binder's connect/disconnect callbacks arrive on the main thread, which is why `NothingGlyphDisplay` keeps its flags in `AtomicBoolean`s: written there, read from the animation thread.
- [Processes and threads overview](https://developer.android.com/guide/components/processes-and-threads) · [Bound services](https://developer.android.com/develop/background-work/services/bound-services)

## Kover class filters and Kotlin's hidden classes
Kotlin compiles lambdas and `object : Interface {}` expressions into extra classes named like `SdkMatrixService$bind$1`. A coverage exclusion for a class must also cover these (`"*.SdkMatrixService$*"`), or the "excluded" code still counts. We found this when the gate failed at 77.5%.

## Activity lifecycle vs a foreground service (M0 Task 5)
An Activity lives only while its screen is in use. When the screen turns off or you press Home, it gets `onStop()`, and Android may destroy it. A **foreground service** keeps running with no screen, as long as it shows an ongoing notification (Android's "this app is doing something" contract). The spike's measurements need the matrix to keep playing while the phone is locked or pocketed, so the session lives in `SpikePatternService`, not the Activity.
- [Activity lifecycle](https://developer.android.com/guide/components/activities/activity-lifecycle) · [Foreground services](https://developer.android.com/develop/background-work/services/fgs)

## `LifecycleService` and owned scopes
`LifecycleService` is a Service that also exposes a `lifecycleScope`: a coroutine scope cancelled automatically in `onDestroy`, like a `context.Context` cancelled at shutdown. Work that must outlive the service, like releasing the matrix *after* the service is gone, runs in the container's process-wide `appScope` instead. Otherwise the cancellation would kill the cleanup itself.
- [Use Kotlin coroutines with lifecycle-aware components](https://developer.android.com/topic/libraries/architecture/coroutines)

## Broadcast receivers: exported, not exported, permission-guarded
A **BroadcastReceiver** reacts to system-wide messages ("intents"). Exported receivers accept them from other apps, which is dangerous unless guarded. The spike's receiver is exported but requires the sender to hold `android.permission.DUMP`, which normal apps can't get and the **adb shell** has. So only you, over USB, can drive it, like an HTTP endpoint behind an admin-only token.
- [Broadcasts overview](https://developer.android.com/develop/background-work/background-tasks/broadcasts)

## `NotificationListenerService`
A service the system binds to when the user grants "notification access". It then receives every posted notification, which is how GlyphWizard's triggers will work (M3). Because it sees everything, the spike logs only package names, never notification text. Android may unbind it (process kill or crash), so the spike also measures how fast it comes back (feeds D28).
- [NotificationListenerService](https://developer.android.com/reference/android/service/notification/NotificationListenerService)

## Foreground service types: `specialUse` vs `shortService`
Since Android 14, every foreground service declares a **type**.
- **`specialUse`** is for cases no other type covers. It needs the `FOREGROUND_SERVICE_SPECIAL_USE` permission plus a written justification in the manifest.
- **`shortService`** needs no permission, but the system calls `onTimeout` after about 3 minutes, and the app gets an ANR ("app not responding") if it doesn't stop within seconds. The agent's turn uses this type (D33), which is why the spike measures it.
- **Background-start restriction:** a background app may not *start* a foreground service, so the probe is fired while the Activity is visible.
- [Foreground service types](https://developer.android.com/develop/background-work/services/fgs/service-types)

## `kotlin.time.TimeSource` and absolute-deadline scheduling
Repeating `delay(period)` adds each frame's work time to the next wait, so the frame rate slowly drifts, like a loop of `time.Sleep`. `GlyphSession` instead waits until *start + n × period*, like Go's `time.Ticker`, so a late frame doesn't shift later ones. Time comes from an injected `TimeSource`, so tests use virtual time: ten "seconds" of 120 fps run instantly and must produce 1200 frames, not 1250.
- [kotlin.time](https://kotlinlang.org/api/core/kotlin-stdlib/kotlin.time/) · [Testing coroutines](https://developer.android.com/kotlin/coroutines/test)

## Mutation checks: proving a test can fail
A test that passes the first time might pass for any code. A quick check is to break the code on purpose (a "mutant") and see whether a test fails. In M0 one mutant survived: rounding the 120 fps period to 8 ms passed the row-sweep test, because the drift only starts around frame 24. The test now also checks late frames.

## The `NothingKey` and how we found it
Manifest `<meta-data>` entries are key/value settings that other software can read from your installed app, like build-time labels on a container image. Nothing's glyph service looks for `NothingKey`. Without it, our frames reached the service (`Ok` every frame, 30 fps), but it logged `setAppMatrixColors, session is null` and lit nothing. The GlyphMatrix README doesn't mention the key. We found it by comparing working open-source apps and Nothing's own example project, all of which declare `NothingKey=test`. Adding just that line fixed it, with no debug mode needed. Two lessons:
- an API that answers "OK" can still be doing nothing, so check what *actually* happens on the device;
- change one thing at a time, so you know which change fixed it.

The service also builds its session a few milliseconds *after* `register()`, so a frame sent immediately is dropped (measured: the first frame at +5 ms dropped, the second at +51 ms shown).

## GitHub Actions (M0 Task 7)
A workflow file (`.github/workflows/ci.yml`) is a CI pipeline definition: on every push and pull request, GitHub starts fresh Linux machines and runs each **job**'s steps, like a Makefile target per stage in a hosted runner. Steps can be shell commands or reusable **actions** (`actions/checkout`, `actions/setup-java`). Because an action is someone else's code running with access to our repo, each is pinned to a full commit SHA (a tag can be moved; a SHA can't), and the workflow's token is read-only. Our jobs only call `scripts/ci.sh`, so a CI run is reproducible on your laptop with the same command.
- [GitHub Actions: workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax) · [Security hardening: pin actions to a SHA](https://docs.github.com/en/actions/reference/security/secure-use)

## Renovate
A bot that watches our version catalog and workflow, and opens a pull request when a dependency has a new release, like Dependabot or a scheduled `go get -u` that you review. `minimumReleaseAge: 14 days` applies our pin rule automatically: a brand-new release (the riskiest moment for a compromised or broken version) is never proposed. detekt updates are never auto-merged (D47).
- [Renovate docs](https://docs.renovatebot.com/)

## Positive controls
A check that something is *absent* (no Nothing SDK classes in the sdkFree APK) passes just as happily when the check itself is broken, for example a wrong path or a typo in the pattern. So `check-sdkfree-apk.sh` runs every check against the full APK too, where the thing **must** be found. If the control fails, the negative check proves nothing. It's the same idea as the detekt canary, and as a lab running a known-positive sample next to the real one.
