## 1. Verdict

- **The roadmap v0.2 is much improved.**
  - It has a testable DoD, per-milestone exit criteria and the D39 order.
  - Safety now comes before the features that need it, and undo comes with the editor.
  - Licence and ID are settled in M0.
  - Most r2 roadmap findings are closed.
- **The agent draft v0.3 was only partly re-synced.**
  - Its header still says v0.2 and D1–D25.
  - §10 still says 20–30 eval tasks; D27 says 60–80 × 3 plus a ~10-task smoke suite.
  - §6 still uses Base/Full exemplar counts that D30 retired.
  - §7 and §11 still put the backgrounding matrix in the M0 spike; the roadmap moved it to M7.
  - These are mechanical, but a spec writer would inherit the contradictions.
- **The biggest quality gaps:**
  - The quality gates have no security, licence-audit, memory, battery, APK-size, migration or release-build gates.
  - "Accessibility pass" is not defined.
  - The agent pillar of the DoD can be "done" with zero Supported models.
  - Two performance budgets can't be measured as written.
- **No fabricated or misrepresented claims are new in this round.** One new claim needs care: the "no frame over 16 ms" budget (see M1).

Findings: **CRITICAL 0 · HIGH 3 · MEDIUM 9 · LOW 11.**

## 3. Findings by severity

### HIGH

**H1. DoD #4 ("use an in-app agent") has no quality bar.** (Roadmap DoD #4, M7 exit; D13, D17, D27)
- **Issue:** The M7 exit asks only that the full suite is *run* and `SUPPORT.md` is published. The M5 exit asks only that the smoke suite *runs* on one model.
- **Consequence:**
  - v1 could ship with every model labelled "Below bar", and still meet the DoD.
  - That's inconsistent with "best possible quality".
  - It's also inconsistent with D13: open-weight models are first-class, yet nothing requires one to reach Supported.
- **Fix:** Add to the DoD and to the M7 exit:
  - (a) At least one model is **Supported** on a route a user can get without a frontier subscription (e.g. an OpenRouter paid open-weight model).
  - (b) At least one **open-weight** model is Supported (D13).
  - (c) Every Supported model passes the safety and flash-gate tasks at 100%, not just on average.
  - (d) State what happens if (a) or (b) fails. Is that a v1 blocker, triggering more KB or tool work, or is it shipped with a documented label? That's an owner decision, but record it now, not at M7.

**H2. Agent draft v0.3 contradicts D27, D30 and D39 in several load-bearing places.** (Draft header, §0, §6, §7, §10, §11, §12)
- **Stale items:**
  - Title line 1 says "Draft v0.2", and lines 5–9 say "incorporates … D1–D25". There's no v0.2 → v0.3 changelog.
  - **§10:** "About 20–30 tasks total" vs D27 / roadmap M5: 60–80 × 3 + a ~10-task smoke suite. The smoke suite isn't mentioned, and there are no CIs.
  - **§6:** "0–1 worked examples per tier" and "0 in-prompt for Full, 1 for Base". D30 says v1 has one tool tier and no Base/Full.
  - **§7 / §11:** "The hardware spike adds a backgrounding matrix" and §11 lists it as an M0 input. Roadmap M7 says "Backgrounding matrix measured [HW]", correctly, because the matrix needs streaming plus FGS code.
  - **§11:** the frame layout still cites the ringtone format [A] (r2 L2).
  - **§12 Q7:** "Synthetic preset" is stale, because Synthetic is no longer a preset (§5 has 5 presets).
- **Why HIGH:** The spec will be written from these three documents. Under "no decisions on assumptions", a spec author has to guess which number wins. Each fix is mechanical.
- **Fix:**
  - One sync pass. Or, in the spec, declare the precedence explicitly: decisions.md > roadmap > draft.
  - Add a "v0.3 changes" table.

**H3. The quality gates lack security, supply-chain and resource gates, and "accessibility pass" is undefined.** (Roadmap "Quality gates", M2/M6/M8 exits)
- **What the app does:**
  - It parses **untrusted input**: GM JSON and `.glyphwiz` via "open with" / SAF, and GIF/WebP decoding in M6.
  - It stores API keys and does LAN cleartext.
  - It runs a long-lived listener with notification access.
  - It ships under an undecided licence with third-party dependencies.
- **What the gates cover:** none of that.
- **Missing gates** (recommended, all on merit):
  1. **Security.**
     - A threat-model section per milestone that touches input, keys or network: M1 I/O, M2 import, M3 notification data, M6 decoders, M7 keys and LAN.
     - **Fuzz / property tests for every parser**: GM, `.glyphwiz`, text-grid, and GIF/WebP size and frame-count limits, i.e. decompression-bomb caps. These belong in the M1 and M6 exits.
     - A pre-release security review, `/security-review` or equivalent, in M8.
     - The notification content the app reads (titles, keyword matching) never leaves the device and never reaches the agent (D12). Make that a test.
  2. **Supply chain.**
     - A dependency licence audit with a generated NOTICE / about-libraries screen, compatible with the M0 licence.
     - Gradle dependency verification (`verification-metadata.xml`), alongside the existing SDK SHA pin.
     - A CI check that the **`sdkFree` APK contains no Nothing SDK classes** (D18). This is the one legal invariant the release depends on, and today nothing tests it.
  3. **Release-build testing.** Run the instrumented/E2E suite against the R8-minified release variant, because R8 can break reflection and serialisation in Ktor / kotlinx.serialization. Add baseline profiles if the cold-start budget needs them.
  4. **Resource budgets** (numbers [P], revised after measurement [HW]):
     - App heap / PSS ceiling during an agent turn. D28 depends on "memory caps", but none are defined.
     - Battery: listener idle drain per day, and cost per trigger playback.
     - APK size for each flavour.
  5. **Migrations / upgrade.** See **M9**.
  6. **Accessibility definition.** Replace "full accessibility pass" (M8) and "editor basics" (M2) with a checklist:
     - Compose accessibility checks / Accessibility Scanner clean on every screen
     - 48 dp touch targets
     - WCAG AA contrast
     - 200% font scale without clipping
     - a **TalkBack strategy for the LED grid** (row/column navigation, announced brightness) and for streaming agent output (polite live-region announcements)
     - reduce-motion honoured in the preview
   - This also covers r2 L7, which is still open in substance.

### MEDIUM

**M1. Performance budgets are partly unmeasurable or missing.** (Roadmap Quality gates; DoD #1)
- **"No frame over 16 ms (JankStats)" doesn't fit this device or this tool:**
  - The 4a Pro runs at 120 Hz, and up to 144 Hz in some apps (GSMArena, Fonearena). Frame budgets are about 8.3 / 6.9 ms, so 16 ms means visible jank on this device.
  - JankStats doesn't use a fixed threshold. By default it flags frames over about 2× the current refresh period (developer.android.com/topic/performance/jankstats).
  - "No frame ever" is also not a stable test.
  - **Fix:** a Macrobenchmark `FrameTimingMetric` budget, e.g. P95/P99 frame duration and jank % on scripted editor interactions. State the refresh mode tested (120 Hz).
- **DoD #1** tests "500 documents listed, opened and saved within the performance budgets below", but no list/open/save budget exists. Add one, e.g. list first paint and open-to-editable time at 500 documents.
- **"Cold start < 1 s"** doesn't say which metric (TTID or TTFD), which build (release, with or without a baseline profile), or which tool (Macrobenchmark `StartupTimingMetric`, median of N).
- **"Event → first LED frame < 150 ms"**: say how it's timestamped, e.g. `onNotificationPosted` entry → the `setAppMatrixFrame` return, with N trials, and whether the screen is on or off.

**M2. "GM round-trip byte-identical on ≥ 10 real community files" is probably the wrong criterion.** (Roadmap M1 exit; DoD #1 "losslessly"; D6, D11)
- **Issue:**
  - Byte identity depends on the source file's whitespace, key order and number formatting, and the GM spec is silent on unknown keys (D11).
  - Real community files will fail byte comparison for reasons that have nothing to do with fidelity.
  - Separately, "losslessly" in the DoD is ambiguous. GM → app → GM can be lossless. `.glyphwiz` → GM *flattens* layers by design (D6, D11).
- **Fix:**
  - The criterion should be **semantic equality**: parsed frames, timing and metadata equal, unknown keys preserved or explicitly dropped and reported.
  - Byte identity should apply only to files the app itself wrote.
  - State the direction in the DoD.

**M3. The no-permission outcome is undefined for the public build.** (DoD #2, #3, #5; D18, D26; roadmap M3)
- **Issue:**
  - `sdkFree` = preview + GM export (D18). Triggers (DoD #3) and LED playback (DoD #2) need the SDK, so a public user without permission gets no daily-use value. That makes order A's rationale moot for them.
  - The roadmap doesn't say whether the trigger UI is present in `sdkFree` (disabled, or as a preview-only "dry run"), or how M3's "SDK bound once" behaves without the SDK.
  - The build-it-yourself path (r2 H1 fix b) is neither adopted nor rejected.
  - Whether the email was sent isn't recorded (G3).
- **Fix:**
  - Specify `sdkFree` behaviour for triggers and the player.
  - Record a decision on the build-yourself path, after confirming the licensee reading with Nothing (question 4 of the email).
  - Log the email's sent date and status in decisions.md.

**M4. D28's safety net isn't measurable.** (D28; roadmap M0, M3, M7; draft §7)
- **Gaps:**
  - "Memory caps" have no value (see H3.4).
  - "Move to a `:triggers` process only if … missed alerts" has no threshold or measurement window, e.g. "> 0 missed alerts in N forced-OOM trials, or any missed alert in a K-day soak".
  - There's no **soak test** with the agent mid-turn while notifications arrive. This is the exact scenario r2 H4 raised.
  - The M7 backgrounding matrix doesn't include the NLS-granted vs not-granted dimension.
  - r2 L8 is untested: does `shortService` block the trigger path from starting a playback FGS?
- **Fix:** Add these to the M3 and M7 exit criteria.

**M5. The [EV] decisions have no deadline milestone (H3 residual).** (Roadmap M5 exit; draft §3, §4, §6)
- **Issue:**
  - Tool count, text-grid encoding, the exemplar 0/1/3 ablation and the working cap are all tagged [EV].
  - M5's exit requires only that the smoke suite *runs*.
  - M7 then builds UI on top of golden-file schemas.
- **Fix:** The M5 exit should require:
  - (a) the ablations run and their results recorded as decisions
  - (b) a full-suite dry run on at least one model with a pass^3 baseline
  - (c) the probe implemented, with recorded-stream tests
  - "Runs" should become "passes at a stated level".

**M6. Eval statistics and the "free variants" route.** (D27; draft §5, §10)
- **CIs:** At 60–80 tasks the CI half-width is about ±0.11. Require Wilson CIs in `SUPPORT.md` and state whether the label uses the point estimate or the lower bound (r2 H2 fix, still not adopted).
- **Free-variant limits:** OpenRouter `:free` limits are 20 req/min, and 50 req/day (1000/day with ≥ 10 credits purchased) (openrouter.ai/docs/api/reference/limits). A full suite is roughly 60–80 × 3 × several steps ≈ 1–3k requests. That's fine under D38, but it means a multi-day run, which the harness must be able to resume.
- **Label scope:** `:free` variants may be served by different providers or quantisations than the paid variant. **Labels must be keyed to (model, route/provider, quantisation if known)**, and a free-variant result must not label the paid route. The draft doesn't state the key.

**M7. "Selective undo surfaced in the UI" in M4 (Timeline) is untagged and conflicts with D36's scope.** (Roadmap M4)
- **Issue:** D36 keeps selective *"Undo this turn"*, which is turn-card and agent UI (M7). M4 runs before any agent exists, so this either means a new feature (selective undo of arbitrary *user* groups, which isn't decided) or it's misplaced.
- **Fix:** Clarify it, tag it [P], and record a decision if it's new scope.

**M8. "Accessibility pass" and "screenshot tests for key screens" can't be checked.** (Roadmap M2, M8)
- **Issue:** See H3.6. "Key screens" also needs a list.
- **Fix:** Name the screens, plus light/dark and font-scale variants.

**M9. Migration and upgrade coverage is limited to `.glyphwiz`.** (Roadmap M1, M3, M8; D29)
- **Not covered by any test:**
  - format versions and migrations for the history sidecar, DataStore trigger rules and settings
  - generator `@N` coexistence (old documents render identically after `@2` lands)
  - backup / restore (D29 exclusions actually take effect)
  - **signed upgrade-install** (vN-1 → vN via Obtainium keeps documents, rules, keys and listener access)
- "Rules persist across app updates" (M3) is the only one present.
- **Fix:** Add fixture-based migration tests per format (M1, M3), a backup/restore test (M2), and an upgrade-install test in M8.

### LOW
