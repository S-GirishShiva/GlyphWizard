## 1. Verdict

- **v0.2 is a real improvement.**
  - No fabricated citations. Every new external claim I checked exists. The Claude thinking-binding rules, the Toolathlon gap and Fisher 2026 are verified word for word.
  - Most r1 findings are closed or materially addressed.
- **What's left is mostly integration risk *between* documents, not inside the agent draft.** Four HIGH items:
  1. The v1 definition of done depends on permission from Nothing that hasn't been obtained, and there's no fallback.
  2. The eval harness is too small to separate the tier thresholds it is supposed to set.
  3. The roadmap builds the harness *after* the agent it is supposed to steer.
  4. The trigger listener (BFGS process) silently changes the agent's backgrounding premise, and nobody has analysed the shared process.
- **The roadmap is the weaker document.**
  - It has no capacity or effort numbers and no per-milestone acceptance criteria.
  - Its order puts safety (flash gate) and undo after the features that need them.
  - The licence and app ID are left to M6.
  - Its main ordering rationale ("triggers have fewer unknowns") is contradicted by the triggers report.
- **decisions.md has drifted from the reports.** D9 isn't amended, D19 has no `maxTier`, and SDK levels, backgrounding, distribution and tier labels aren't recorded. D24 records approval of a roadmap that is still marked "for review".

**Recommendation:**
- One more short round (r3), scoped to the roadmap plus a decisions.md sync. The agent draft only needs the edits listed below.
- No new research is needed before r3, except G1–G3 (§6).

Findings count: **CRITICAL 0 · HIGH 4 · MEDIUM 12 · LOW 11**.

## 4. Severity-ranked new findings

### HIGH

**H1. The v1 definition of done is gated on an unobtained permission and has no fallback.** (Roadmap DoD #2 + #5, M0, M6; draft §8; D18; [AF] CI)
- **Issue:** DoD #2 (play on the physical matrix) and #5 (install from GitHub Releases via Obtainium) can only both hold if Nothing permits distributing an APK containing the SDK.
- **Evidence:**
  - EULA §2.1(c) and §2.2 (r1, re-cited in [TAP]).
  - [TAP]: "The GDKsupport email gates every channel except an SDK-free build."
  - [AF]: "CI never fetches the Nothing `.aar`… so CI builds `sdkFree` only", and the release job publishes `app-sdkFree-release.apk`.
  - Nowhere is it recorded whether the email was sent or what was answered.
- **Fix:**
  - (a) Send the email in M0, using [TAP]'s four explicit questions, and record its status in decisions.md.
  - (b) Write the fallback into the DoD now: if there's no answer by M6, release `sdkFree` on GitHub plus a documented "build the full flavour yourself" path. The user then fetches the SDK, so the user is the licensee. Confirm that reading with Nothing too.
  - (c) Reword DoD #5: "full flavour via Obtainium *if permitted*; otherwise sdkFree + build-from-source".

**H2. The eval harness can't statistically resolve the tier thresholds it is supposed to set.** (Draft §5 "pass^3 ≥ 0.6 / ≥ 0.7", §10 "About 20–30 tasks"; roadmap M6 "~20 tasks"; D17)
- **Issue:** D17 makes harness results the *authority* for support, and the draft distinguishes Base from Full by 0.1 of pass^3.
- **Evidence [C]:**
  - At n = 20, an observed 12/20 = 0.60 has a Wilson 95% CI of about 0.39–0.78. At n = 30, 18/30 has about 0.42–0.75.
  - Toolathlon (row 5) shows pass@1 − pass^3 gaps of 8–18 pp on its own task set, so run-to-run variance is large.
  - [TPM] itself: multi-turn has "notably higher variance" across seeds.
  - Families are smaller still: the 5 non-English tasks would be reported "per model".
- **Fix:**
  - Publish CIs in `SUPPORT.md`, and gate on the **CI lower bound**, or accept that v1 has a single "Supported" bar.
  - Size the suite from the decision you want to make. Distinguishing 0.6 from 0.7 at ±0.05 needs on the order of 100+ task-runs per model, which costs real money for a solo developer, so the user must budget it (draft §12 Q10).
  - Drop the per-language and per-family gating claims in v1.

**H3. The roadmap builds the eval harness after the agent it is meant to steer.** (Roadmap M5 → M6; draft §3 "[EV]", §6 "[EV]", §10)
- **Issue:** Many v1 design choices are marked "settled by the eval harness": tool count, text-grid encoding, exemplar 0/1/3 ablation, working caps, tier thresholds. Yet `:evals` lands in M6, after the agent ships its UI.
- **Consequence:** Every [EV] choice is made blind until the end, and fixing them then means reworking M5. Tool schemas are golden files, which makes them expensive to churn late.
- **Evidence:**
  - `:agent` and `:evals` are pure JVM and need nothing from M2–M4 (draft §2; [AF] module rule `:evals → :core, :agent`).
  - [AF]: recorded transcripts "double as `:evals` fixtures".
- **Fix:**
  - Split M5:
    - **M5a**: `:agent` loop + adapters + `FakeProvider` + `:evals` CLI + the probe, JVM-only. It can start right after M1.
    - **M5b**: the Android integration (chat UI, Keystore, FGS, turn cards).
  - Run a first small harness round between M5a and M5b. M6 keeps only the final `SUPPORT.md` run.

**H4. The trigger listener changes the agent's backgrounding premise, and two must-haves now share one process unanalysed.** (Draft §7 Backgrounding; [TAP] R3; [TRG] TL;DR 1; roadmap M0/M4/M5)
- **Issue:** The draft's justification for `shortService` is "without an FGS a streaming turn dies about 10 s after the user leaves the app". That's true only when the process becomes *cached*.
- **Evidence:**
  - Once notification access is granted (D21: triggers are a v1 must-have), the system binds our NLS with `BIND_FOREGROUND_SERVICE | BIND_NOT_PERCEPTIBLE` (verified, row 8). The process sits at adj ≈ 250: not cached, not frozen.
  - For trigger users, then, the turn would keep streaming in the background *without* the FGS. The FGS's real job is only bounding spend, which the app could do itself.
  - Conversely, the agent's memory (Ktor buffers, transcripts, baked frames) now lives in the process that must stay alive for alerts. AOSP lowers listener priority *because* listeners cause "extreme memory pressure", and Android 17 adds `MemoryLimiter` ([TAP]). An agent OOM or crash takes the trigger runtime down with it.
  - Neither [TAP] nor [TRG] mentions the other's process model.
- **Fix:**
  - (a) Add NLS-enabled vs NLS-disabled as a dimension of the backgrounding matrix (draft §11, roadmap M0) and of the process-state check (`dumpsys activity processes`).
  - (b) Decide explicitly whether the NLS runs in a separate `android:process`. That isolates triggers from agent crashes, but needs `MultiProcessDataStoreFactory` ([AF] already notes this) and a second `GlyphMatrixManager` binding per process (watch [TRG] L1/L2).
  - (c) Keep the 150 s budget as an *app-level* rule, independent of whether the FGS is needed.
  - Record the outcome as a decision.

### MEDIUM

**M1. The epoch tuple is narrower than the evidence requires.** (Draft §6 Epochs; [TPM] §3)
- **Issue:** The draft's epoch is (model, endpoint, tool-schema version, kbVersion, app version). [TPM]'s is `(endpointId, modelId, accountKeyFingerprint, toolsetHash, systemPromptHash, kbVersion)` plus tier changes.
- **Consequences:**
  - Without the key fingerprint, a key swap on Sonnet/Haiku 5.5 replays account-bound thinking blocks, which are *silently dropped* (row 2). Reasoning degrades with no signal.
  - Without a system-prompt hash, any change to the generated device card, the skill index or the vocabulary map within one app version (e.g. a document with a different `DeviceProfile`) mutates `system` and triggers the 400.
- **Fix:** Adopt [TPM]'s tuple, plus `deviceProfileId` and tier.

**M2. The 32k minimum context leaves no room for output.** (Draft §5 "context ≥ 32k" vs §6 "~30k for Base")
- **Issue:** A Base model at exactly 32k gets a 30k working cap. That leaves ~2k for `max_tokens`, including reasoning tokens.
- **Evidence:** [TPM]'s probe budget estimates ~5–7k *input* per request, and reasoning models routinely emit several thousand output tokens per step.
- **Fix:** Define the working cap as `min(30k, declaredContext − maxOutput − margin)`, and set `maxOutput` per endpoint. Or raise the gate. Tag both [P].

**M3. History-cap numbers diverge across four documents, and Auto Backup fails all-or-nothing.** (D9; [AF] §4.2; [TES] R5; draft §8; roadmap M1)
- **Evidence:**
  - D9: "~200 steps/256KB" (not amended).
  - [AF]: sidecar "capped at ~200 steps / 256 KB (D9)" and "Backup: fine to include".
  - [TES]: "~4 MB compressed per document".
  - The draft says "sized by compressed bytes" with no number. The roadmap cites "D9 as revised", but no revision exists.
  - Auto Backup (verified): "If the amount of data is over 25 MB, the system… doesn't back up data to the cloud". All of it, including documents and trigger rules. Seven documents at the [TES] cap would disable backup silently.
- **Fix:** Amend D9 with one number. Exclude `*.history.gz` from cloud backup, or cap total history, and keep documents and rules in backup. Update [AF].

**M4. v1 ships one tool tier, but the tier machinery is specified as if there were two.** (Draft §1, §3, §5, §6; D19; roadmap M5 "Base-tier tools", v1.1 "full-tier tools")
- **Issue:**
  - [TPM] defines Full as "full toolset pass^3 ≥ 0.7 and no regression vs base". With no Full toolset in v1, that can't be measured.
  - The only v1 tier difference is the exemplar count (0 vs 1), and that is gated by the 0/1/3 ablation anyway.
  - The draft cites "minTier/maxTier [D19]", but D19 only defines `minTier`.
- **Fix:**
  - v1: Supported / Unsupported (plus provisional), plus a per-model-family exemplar flag set by the ablation.
  - Reintroduce Base/Full with the v1.1 tools.
  - Record the labels and the `maxTier` amendment in decisions.md (closes r1 M10).

**M5. The roadmap puts safety after the features that need it.** (Roadmap M2 "▶ LEDs", M3 "Flash-risk warning", M4 triggers; [TES] §R7 policy items 2 and 5)
- **Issue:** [TES] requires a one-time confirmation before **Play on LEDs** and GM export of a FAIL animation, and recommends that FAIL animations "need explicit opt-in to be assigned to a trigger". The roadmap gives LED playback in M2 with no flash gate, adds the warning only in M3, and M4 has no trigger opt-in.
- **Evidence:** `analyze.flash` is pure `:core` code (O(LEDs × frames)), so nothing stops it from shipping in M1.
- **Fix:** Move `analyze.flash` + golden tests to M1, the gate to M2, and the trigger opt-in to M4 (also an open [TRG]/[TES] question for the user).

**M6. Missing roadmap work items.**
- **Onboarding & permissions UX:** Restricted-settings walk-through ([TRG] risk table: "High… setup drop-off"), notification-access disclosure, and a "Sound only" settings explainer for priority clashes ([TRG] L5).
- **Settings screen:** providers, spend caps, reduce-flashing, models.dev opt-in, event-log opt-in.
- **Error handling and crash capture with no backend:** local crash log + the debug bundle. `ApplicationExitInfo` logging is in the draft but not the roadmap.
- **Backup rules** (M3 above), and DataStore/sidecar format migrations alongside `.glyphwiz` migrations.
- **Developer verification:** register before the 2027 global rollout (row 13). The free limited account (≤ 20 devices) doesn't cover a public release.
- **Licence, NOTICE and the permanent application ID belong in M0, not M6.**
  - The ID is bound to the signing key and Obtainium tracking.
  - The GPL §7 exception "only the copyright holder can grant", and "contributions must come under the same terms" ([AF]). It has to exist before any outside contribution or public push.
- **Scaffold migration** (minSdk 24 → 35, target 37 → 36, `com.example`, Views → Compose) isn't listed in M0.
- **String resources from day one** ([TAP] i18n).

**M7. The roadmap's ordering rationale is untagged and contradicted by evidence.** (Roadmap "Order rationale")
- **Issue:** It says triggers "have fewer unknowns". [TRG] lists many open unknowns:
  - restricted settings with Obtainium [U]
  - 4a Pro face-up/pocket suppression [U]
  - rival listeners fighting for the panel [S]
  - ringtone/notification ordinals [S]
  - priority behaviour after OS updates (risk "Medium")
  - event-to-frame latency of < 150 ms "to be measured"
- **Fix:** Tag the rationale [P] and restate it honestly. Triggers come early because they make the app usable every day, *and* because their unknowns are platform risks best surfaced early. Note that triggers depend only on M1 (baker, templates) and M2 (LED output), not on M3. If the user values daily use, M4 could precede M3.

**M8. Undo UI arrives after the editor that needs it.** (Roadmap M1/M2/M3)
- **Issue:** History is in M1 and the editor in M2, but "Persistent undo / redo" UI is only in M3. An editor without undo for a whole milestone is unusual, and the M2 editor is the first real UI test of D9.
- **Also:** Turn cards are agent UI ([TES] three states). They belong in M5b, not M3.
- **Fix:** Undo/redo toolbar in M2; turn cards in M5b.

**M9. Image import in the agent exceeds D25, and source-image retention is unspecified.** (Draft §3 "Image import"; D25 "agent may call it later")
- **Issue:** The draft makes `add_clip(source=image)` re-runs a v1 agent capability. D25 says "later", and roadmap M5 doesn't list it.
- **Hidden cost:** Re-running with new parameters requires keeping the source image (in the document or a sidecar). That has size, export and privacy effects: a photo of a person inside an exported `.glyphwiz`. The user also has to know that the image itself isn't sent to a text-only model.
- **Fix:** Either defer the agent hook (per D25) or specify retention (app-private, excluded from exports by default) and add it to M5.

**M10. decisions.md lags the reports. Under the owner's ethos, the log should be the source of truth.**
- **Missing or stale entries:**
  - D9 not amended.

**M11. Persisting the epoch-keyed wire cache is optional complexity in v1.** (Draft §7 Persistence)
- **Issue:** A persisted wire cache only matters for resuming the *same* epoch after process death.
- **Evidence:** The draft already compacts on any epoch change. [TPM]'s "simple compaction (recommended)" is Anthropic's own advice.
- **Fix:** Keep the wire cache in memory and treat process restart as an epoch boundary (compact). That drops one persistence format and its migration story, at the cost of losing reasoning blobs after a kill, which is rare.

- **DoD testability:**
